# Развертывание и Запуск Orbitra

Проект Orbitra оптимизирован для быстрого старта без сложной настройки окружения. В основе лежит лёгкий стек **PHP + SQLite + Nginx** — без отдельного сервера БД (нет ClickHouse, Redis или MySQL).

## Системные требования

Orbitra хранит всё в одном файле SQLite, поэтому требует значительно меньше RAM, чем трекеры на ClickHouse, и работает на самых дешёвых VPS.

**Базовые (обязательные):**

- **CPU:** 1 vCPU (x86_64)
- **RAM:** 1 GB (рекомендуется 2 GB)
- **Диск:** 20 GB SSD
- **ОС:** Ubuntu 20.04 / 22.04 / 24.04 или Debian 11 / 12
- Чистый сервер без панели управления; доступ root/sudo

**Подбор по объёму трафика (ориентир):**

| Кликов в сутки | RAM | CPU | Диск |
|---|---|---|---|
| до ~100 000 | 1–2 GB | 1–2 vCPU | 20 GB SSD |
| ~100 000 – 500 000 | 2–4 GB | 2 vCPU | 40 GB SSD |
| ~500 000 – 1 000 000 | 4–8 GB | 4 vCPU | 80 GB SSD |

> ✅ **Проверено на практике:** Orbitra стабильно работает на VPS **2 vCPU / 2 GB RAM / 20 GB SSD** (Ubuntu 24.04) при небольшом трафике — удобная и недорогая отправная точка. Верхние строки таблицы — это запас под более высокий трафик, а не жёсткое требование.

> 💡 **Почему меньше, чем у Keitaro?** Keitaro хранит клики в ClickHouse + Redis + MySQL, поэтому его требования по RAM растут до 64 GB на миллионах кликов в сутки. У Orbitra всё в одном файле SQLite — узкое место не RAM, а дисковый I/O и однопоточная запись SQLite. Для низких и средних объёмов (в режиме WAL) этого достаточно; для устойчивых **миллионов кликов в сутки** с тяжёлой аналитикой архитектурно лучше подходит трекер на колоночной БД (как Keitaro).

> 💡 При установке на сервер с 1 GB RAM добавьте 1–2 GB swap: сборка фронтенда (Vite) — самый требовательный к памяти шаг. Сам трекер работает и на 1 GB.

## Быстрая Автоматическая Установка (Production)

Самый быстрый и правильный способ запуска проекта на сервере — использование встроенного инсталлятора. 

1. Убедитесь, что у вас "чистый" Linux сервер (Ubuntu 20.04/22.04).
2. Выполните команду от имени root/sudo:
   ```bash
   wget -O orbitra-install.sh https://raw.githubusercontent.com/fenjo26/Orbitra.link/main/install.sh && bash orbitra-install.sh
   ```
   Загрузка вынесена в отдельный шаг намеренно: `wget -qO- … | bash` при неудачной
   загрузке молча передаёт в bash пустоту, и установка «завершается» без единой
   строки вывода. Так неудачная загрузка останавливается на `&&`, и wget пишет причину.
3. Скрипт сам установит Nginx, PHP 8+, SQLite, скачает код фронтенда и настроит сертификаты HTTPS.

> **Первый вход:** учётной записи «по умолчанию» нет. После установки откройте `http://<ваш-домен>/admin.php` — при первом запуске Orbitra запустит мастер первичной настройки, где вы создадите собственного администратора (логин ≥ 3 символов, пароль ≥ 6 символов, часовой пояс и язык).

### Доступ к панели по IP

Панель всегда доступна по адресу сервера — `http://<ip>/admin.php` — сколько бы доменов вы ни привязали и какие бы из них потом ни удалили. За это отвечает catch-all блок, который Orbitra ставит первым в конфиге Nginx; сертификаты выписываются через `certbot certonly --webroot`, поэтому Certbot конфиг не переписывает.

`https://<ip>/admin.php` тоже работает, но с предупреждением браузера: Let's Encrypt не выдаёт сертификаты на голые IP, поэтому используется самоподписанный.

Если панель всё-таки перестала отвечать — например, конфиг Nginx правили руками, — пересоберите его из базы:

```bash
sudo php /var/www/orbitra/cli/nginx_sync.php
```

Команда заодно чинит renewal-конфиги Certbot, оставшиеся от прежнего способа выписки, и генерирует самоподписанный сертификат. **После обновления с версии ниже 0.9.6.4 выполните её один раз.**

### Секретный путь к панели

`/admin.php` — первый адрес, который перебирает всё, что сканирует диапазоны IP хостеров. В *Настройки → Система → Путь к админ-панели* его можно сменить на произвольный: панель переедет на `/ваш-путь`, а `/admin.php` начнёт отдавать 404.

Это прячет панель, но не заменяет пароль: `/api.php` по-прежнему отвечает и проверяет авторизацию сам.

Если путь забыт, вернуть панель на место можно с сервера:

```bash
php /var/www/orbitra/cli/admin_path.php          # показать текущий путь
php /var/www/orbitra/cli/admin_path.php reset    # вернуть /admin.php
```

### Ограничение доступа к панели по IP

В *Настройки → Система → Доступ к панели* задаётся список IP/CIDR. Поле пустое — панель открыта всем (по умолчанию). Заполненное — вход в `admin.php` и в авторизованные вызовы `api.php` разрешён только с указанных адресов (IPv4 и IPv6, по одному в строку; поддерживаются диапазоны вида `10.0.0.0/8`, `2001:db8::/32`). Это дополнительный слой поверх пароля и секретного пути, а не их замена.

### Очистка старых данных (retention)

Поля *Хранение логов* и *Хранение архива* в системных настройках задают, сколько дней хранятся клики/конверсии и архивные записи. Очистку нужно запланировать в cron — она не запускается автоматически:

```bash
0 3 * * * php /var/www/orbitra/cli/cleanup_cron.php >> /var/log/orbitra_cleanup.log 2>&1
```

Скрипт удаляет данные порциями (чанками), чтобы не блокировать БД, и пишет результат в `cleanup_cron_last_run` в настройках.

### Автооптимизация ротации лендингов/офферов

Переключатель *Auto* у списка лендингов или офферов в стриме включает автопересчёт весов по выбранной метрике (подтверждённые продажи, CR, EPV, EPC, ROI). Пересчёт выполняется кроном, путь клика не меняется — роутер читает веса из `schema_custom_json` как и раньше. Каждая ротация несёт свой интервал переоценки, поэтому крон должен запускаться часто (не due-стримы пропускаются дёшево):

```bash
*/5 * * * * php /var/www/orbitra/rotation_optimiser_cron.php >> /var/log/orbitra_rotation.log 2>&1
```

Метрики берутся из того же движка, что и отчёты (`core/ReportMetrics.php`), за скользящее окно (по умолчанию 7 дней); клики safe-page исключаются. Каждое изменение веса пишется в журнал `stream_rotation_log` — последние решения видны в карточке стрима под переключателем Auto. Пока Auto включён, веса принадлежат крону: ручной ввод заблокирован, а сохранение кампании не откатывает пересчитанные веса.

## Локальная Разработка (React & PHP Server)

Если вы планируете изменять исходный код фронтенда (`React`) и визуальную часть трекера, вам потребуется локальная связка PHP + Vite.

### Часть 1: Запуск Backend API
Откройте первый терминал и запустите встроенный PHP сервер с роутером:

```bash
cd Orbitra
php -S localhost:8080 router.php
```
*Этот сервер будет принимать API запросы и редиректы.*

### Часть 2: Запуск Frontend (Vite)
Откройте второй терминал, установите npm пакеты и запустите dev-сервер:

```bash
cd Orbitra/frontend
npm install
npm run dev
```

После этого откройте в браузере `http://localhost:5173`. Все API запросы с фронтенда будут автоматически проксироваться (через `vite.config.js` proxy) на `http://localhost:8080/api.php`, что позволяет избежать проблем с CORS и сессиями в режиме разработки.

## Сборка для Продакшена (Production Build)

После того как все изменения во фронтенде завершены, необходимо "собрать" React приложение в статические JS/CSS файлы, которые будет отдавать ваш Nginx/Apache или встроенный роутер.

```bash
cd Orbitra/frontend
npm run build
```

Эта команда сгенерирует оптимизированные файлы в папку `frontend/dist/`. Загрузите весь проект Orbitra (включая папку `frontend/dist`) на ваш VPS сервер.

## Настройка Интеграции Telegram Bot

1. Откройте Telegram и найдите официального бота `@BotFather`.
2. Введите команду `/newbot`, следуйте инструкциям и получите токен (API Token) вида `1111:AAABBBCCCDDD`.
3. Откройте панель администратора Orbitra -> **Интеграции -> Telegram Bot**.
4. Вставьте токен в поле и нажмите **Подключить**. Ваш домен (откуда вы сидите) автоматически установится как **Webhook** для Телеграма.
5. Напишите созданному боту `/start` из вашего Телеграмм аккаунта. 
6. Включите переключатели уведомлений на той же странице интеграций.
