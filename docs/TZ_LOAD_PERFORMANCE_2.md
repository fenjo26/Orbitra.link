# ТЗ: клик без ожидания диска — постоянное соединение SQLite, чекпоинты в фоне, лимиты nginx, настраиваемая защита от двойных кликов

Источник: нагрузочный тест 16–17.11.2026 по методике CPA.RIP «Нагрузочное тестирование 4 бесплатных self-hosted CPA-трекеров», диагностика на стенде, эксперимент с двумя правками.
Все материалы: `docs/loadtest-2026-11/` (`DIAG.md`, промты агентов, архивы результатов; архивы `*.tar.gz` в git **не добавлять**).
База: v1.9.5 (`c43ce94`). Цель: **v1.9.6**. Статус: не начато.

## 0. Зачем

Стенд: VPS 4 vCPU / 10 ГБ, Ubuntu 24.04, Orbitra 1.9.4, поставленная `install.sh` без ручных правок, гео-базы в один клик. Генератор k6 на соседнем VPS. Диск у хостера сетевой: `fdatasync` p50 8,5 мс, p99 28 мс, max 92 мс. Это обычная ситуация для дешёвых облачных VPS, на таких серверах сидит большинство наших пользователей.

| | Как ставится сейчас | С двумя правками из этапов 1 и 3 (эксперимент) |
|---|---|---|
| Один клик с записью, без нагрузки | p50 24 мс, p99 66 мс | p50 3,8 мс, p99 11 мс |
| `fdatasync` на клик | 4,00 | 0,04 |
| Уники: максимальная пройденная ступень | 320 rps | 480 rps (3 из 3), а также 640 и 800 без ошибок |
| Неуники (пул 10 000) | 160 rps | 320 rps (3 из 3) |
| p99 на 160 rps, уники | 1 295 мс | 148 мс |
| HTTP 500 | на 320–480 (`768 worker_connections are not enough`) | нет |

**Причина 1 (этап 1).** Каждый запрос PHP-FPM открывает новое соединение SQLite и закрывает его в конце. Когда закрывается последнее соединение, SQLite делает чекпоинт и **удаляет WAL-файл**. Следующий запрос создаёт WAL заново: `fdatasync` заголовка WAL, `fdatasync` каталога, `fdatasync` коммита и `fdatasync` чекпоинта на закрытии. Это 4 синхронизации диска на каждый клик. Подтверждено `strace` на стенде и в отдельном окружении.

**Причина 2 (этап 2).** С постоянным соединением осталась одна проблема: автоматический чекпоинт (`wal_autocheckpoint = 1000` страниц) выполняется **внутри запроса клика**, которому не повезло, и этот посетитель ждёт `fdatasync` основной базы. Отсюда хвосты p99 ~100–150 мс при медиане 4 мс и единичные таймауты на 480 rps (8 и 17 на ~86 тыс. запросов при CPU трекера 40%). У Binom на той же ступени p99 14 мс.

**Причина 3 (этап 3).** `install.sh` не трогает `worker_connections 768` в nginx. Это был этап 4 сентябрьского ТЗ по нагрузке (сам тот файл в репо не коммитился), он так и не сделан.

**Причина 4 (этап 4).** Защита от двойных кликов (повтор той же пары IP+UA в пределах 2 с получает cid предыдущего клика и не создаёт строку) жёстко зашита. По критерию CPA.RIP «каждый запрос записан отдельно» профиль неуников из-за неё проваливается на любом железе.

## Этап 1. Постоянное соединение SQLite для веб-запросов (P1)

**Где:** `config.php`, строки ~16–23 (`$pdoOptions`, `new PDO("sqlite:" . $db_file, …)`).

**Сделать.**
1. В `$pdoOptions` добавить `PDO::ATTR_PERSISTENT => (PHP_SAPI !== 'cli')`. Для `cli-server` (тесты на `php -S`) соединение тоже постоянное, это правильно: тесты должны работать в том же режиме, что прод.
2. Сразу после `new PDO(...)`: если `$pdo->inTransaction()`, то `rollBack()`. Это защита от транзакции, брошенной предыдущим упавшим запросом того же воркера. Обернуть в `try`: ошибка отката не должна ронять запрос, её нужно записать в `error_log`.
3. **Аудит мест, которые подменяют или удаляют файл базы**, пока работает php-fpm. Воркеры с постоянным соединением держат старый inode: после подмены они продолжат писать в удалённый файл, и данные потеряются. Найти все (`grep` по `orbitra_db.sqlite`, `$db_file`, `rename(`, `copy(`, `unlink(`, `VACUUM INTO`, `.sqlite` в `*.php` и `*.sh`, кроме `tests/`, `vendor/`, `var/`). Известные:
   - `install.sh` ~372–420: переустановка сохраняет базу в `/tmp` и возвращает её `mv`. Php-fpm должен быть **остановлен до `mv`** и запущен после (сейчас рестарт только на ~703). Исправить порядок.
   - `cli/add_antibot_stream.php`: `VACUUM INTO` создаёт копию, подмены нет. Проверить и записать в отчёт.
   - Если найдётся ещё что-то (восстановление из бэкапа, импорт), то: остановить fpm → заменить → запустить, либо явно запретить замену при работающем fpm. Каждое место перечислить в отчёте.
4. Отдельные короткоживущие соединения (`session_bootstrap.php` ~74 — файл в корне репо, не в `core/`; `api.php` ~11572 `$freshPdo`; `core/SessionReplay.php` ~228) оставить **непостоянными**. Комментарий в `api.php` ~11566 про «PDO, прикреплённый к старому снимку WAL», перечитать: при постоянном соединении он становится ещё важнее. `$freshPdo` должен остаться отдельным непостоянным соединением.
5. Все PRAGMA, которые `config.php` выполняет на каждом запросе (`busy_timeout`, `journal_mode`, `synchronous`, `foreign_keys`), оставить: они дешёвые и гарантируют одинаковое состояние соединения.

**Тесты** (`tests/sqlite_persistent_connection_test.php`, HTTP против `php -S`):
- 50 последовательных уникальных кликов → файл `-wal` существует всё время между запросами (сейчас он исчезает после каждого);
- запрос, который бросает исключение посреди транзакции (тестовый эндпоинт только в харнессе или существующий путь, который можно уронить), → следующий запрос того же воркера видит `inTransaction() === false` и его запись коммитится;
- запрос A оставляет недочитанный `SELECT` (поведение «старого кода»), запрос B того же воркера после коммита из другого соединения видит новую строку, то есть снимок не протёк между запросами;
- `install.sh`: статическая проверка не годится. Достаточно описать в отчёте фактический порядок команд и доказать его прогоном на чистом Ubuntu 24.04 (`cli/os_matrix.sh` или VM): переустановка поверх существующей базы → клики после переустановки есть в базе.

## Этап 2. Чекпоинты WAL вне пути клика (P1)

**Цель:** ни один веб-запрос в нормальном режиме не выполняет чекпоинт (нет `fdatasync` основной базы внутри клика), а WAL при этом не растёт бесконечно.

**Сделать.**
1. **Веб-соединения:** `PRAGMA wal_autocheckpoint = 10000` (~40 МБ). Это аварийный предохранитель на случай, если фоновый чекпоинт не работает. В нормальном режиме до него не доходит. `0` не ставить: без фонового процесса WAL вырастет бесконечно.
2. **Фоновый чекпоинт в `cli/click_spool_cron.php`.** Новый крон не добавлять: этот уже стоит на всех установках (install.sh, server_setup.sh) и работает в режиме single-flight через flock. После всей существующей работы тика (сборка индекса, бэкфилл, replay спула, отложенные постбеки) — цикл до ~55 с от старта тика: каждые **2 с** `PRAGMA wal_checkpoint(PASSIVE)`. Если WAL > 64 МБ и активных записей нет, `wal_checkpoint(TRUNCATE)`. Логировать раз в тик: число чекпоинтов, максимальный размер WAL, максимальная длительность чекпоинта. Если существующая работа тика заняла почти всю минуту, цикл просто короче, это нормально.
3. `PRAGMA journal_size_limit = 67108864` (64 МБ) на всех соединениях, чтобы файл WAL после чекпоинта не оставался огромным.
4. Если в окружении нет cron (не наш стандартный сценарий), включается предохранитель из п. 1. Это поведение описать в CHANGELOG одной строкой.
5. На панели в «Статусе системы» (где уже показывается SQLite) — размер WAL и время последнего фонового чекпоинта. Новые строки во все 7 локалей. Если последний чекпоинт был больше 5 минут назад, показывать предупреждение «фоновая задача не работает, проверьте cron» со ссылкой на команду `server_setup`.

**Тесты** (`tests/wal_background_checkpoint_test.php`):
- веб-соединение получает `wal_autocheckpoint = 10000` (прочитать PRAGMA через HTTP-эндпоинт харнесса или из соединения в том же процессе `php -S`);
- 2 000 уникальных кликов через HTTP → WAL растёт (чекпоинтов в запросах нет);
- один прогон `click_spool_cron.php` с укороченным циклом (параметр или env для теста) → WAL сброшен, строки на месте, в логе есть запись о чекпоинтах;
- клики во время работы фонового чекпоинта не падают и не уходят в спул.

**Замер в отчёте** (на любой машине; на сетевом диске нагляднее): `strace -f -c` по воркерам php-fpm при работающем кроне. `fdatasync` в воркерах ≈ 0 на клик; все `fdatasync` основной базы — в процессе крона.

## Этап 3. Лимиты nginx на сервере (P1, server_setup v2)

**Сделать.**
1. `cli/server_setup.sh`: `SERVER_SETUP_VERSION=2`, новый шаг «nginx limits» (только если nginx установлен; на Apache-установках пропустить с NOTE):
   - в `/etc/nginx/nginx.conf`: `worker_connections` → `4096`, если сейчас стоит стоковое значение (`768` или `1024`). Значение, которое кто-то выставил руками и которое больше 4096, не трогать;
   - на верхнем уровне `worker_rlimit_nofile 16384;`, если директивы нет;
   - правка через бэкап → `sed` по точному шаблону → `nginx -t` → при ошибке откат из бэкапа и сообщение, без перезаписи файла целиком; затем `systemctl reload nginx`;
   - идемпотентно: повторный запуск ничего не меняет и пишет «уже настроено».
2. `core/server_setup.php`: `ORBITRA_SERVER_SETUP_REQUIRED = 2`. Существующие установки (их больше 1000) увидят в панели команду обновления. Текст баннера для этого шага — «рекомендуется: повышает предел нагрузки», а не ошибка. Проверить, что баннер не блокирует обновление и не пугает формулировкой. Строки во все 7 локалей.
3. `install.sh` уже вызывает `server_setup.sh`, поэтому новые установки получат шаг автоматически. Проверить, что это так, и **не** дублировать правку в `install.sh`.
4. Проверить на всех ОС из `cli/os_matrix.sh`.

**Тест:** shell-тест на копии стокового `nginx.conf` из Ubuntu 24.04 и Debian 12: шаг применён, `nginx -t` проходит (если nginx есть в окружении теста), повторный запуск — без изменений; конфиг с ручным `worker_connections 8192` не тронут.

## Этап 4. Настраиваемое окно защиты от двойных кликов (P2)

Решение Руслана может поменять значение по умолчанию. ТЗ делает механизм, дефолт остаётся прежним: **2 с**.

**Сделать.**
1. Настройка `click_debounce_seconds` в `settings`: целое 0–10, по умолчанию 2. `0` — защита выключена, каждый запрос пишет свою строку.
2. `orbitraFindDebounceDuplicate()` (`core/click_logger.php`) и оба места вызова (`index.php`, `click.php`): окно берётся из настройки (из уже загруженного `$settings`, без лишнего запроса к базе); при `0` поиск вообще не выполняется. Интервал в SQL — только целым числом из валидированной настройки, никакой подстановки строк.
3. UI: поле в общих настройках трекера рядом с другими параметрами учёта кликов. Подсказка (7 локалей): «Повтор с того же IP и браузера в пределах N секунд считается тем же кликом: новая строка не создаётся, посетитель получает subid первого клика. 0 — записывать каждый запрос».
4. В `docs/` (вики, если есть раздел про учёт кликов) — абзац про эту настройку и про то, что в нагрузочных тестах вида «каждый запрос записан отдельно» её нужно ставить в 0.

**Тесты** (дополнить `tests/click_debounce_test.php`):
- `2` (по умолчанию) — поведение 1.9.5 без изменений (те же ассерты, что сейчас);
- `0` — два одинаковых запроса за 1 с → две строки, два разных cid, оба в базе;
- `5` — повтор через 3 с → тот же cid; через 6 с → новая строка.
