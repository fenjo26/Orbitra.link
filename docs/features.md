# Основные Функции Orbitra v1.1.8

Полный обзор функциональности трекера Orbitra — современного аналога Keitaro Tracker.

## 🆕 Новое в v1.1.8

- **Фильтры по сущностям в «Аналитике»** — мультивыбор кампаний, офферов и лендингов в режимах Тренд и Когорта: дропдауны с группами (галочка на группе выбирает все её элементы), поиск внутри списка, «Выбрать все» / «Сбросить», бейджи активных фильтров с быстрым сбросом. Выбор уходит в параметризованные `IN (...)`-запросы через whitelist-поля `campaign_id` / `offer_id` / `landing_id` (последнее добавлено в whitelist'ы трендов и когорт в этом релизе).
- **Исправлено: фильтры из прошлой попытки не появлялись** — коммиты фичи не пересобирали `frontend/dist`, и панель продолжала отдавать старый бандл; Когорта к тому же молча игнорировала выбранные фильтры (эффект загрузки не перезапускался при выборе). Дропдауны сущностей переведены на лёгкие эндпоинты `campaigns_simple` / `offers_simple` (оба теперь отдают `group_id`), пустое состояние «Ничего не найдено» переведено на все 7 языков. **После обновления один раз сделайте hard-reload панели (Ctrl/Cmd+Shift+R)** — имя файла `index.js` стабильное, браузеры кэшируют старую сборку.

## 🆕 Новое в v1.1.7

- **Хотфикс ассетов лендингов за nginx** — генерируемая локация `/_internal_assets/` содержала вложенный regex-блок под `alias`; вложенные regex-локации ломают наследование alias в nginx, и передача ассетов уходила в редирект-лупы (500). Блок выпрямлен: без вложенных локаций — белый список расширений и MIME-проверки остаются в PHP, где они и были. PHP-фолбэк дополнительно распознаёт сломанный вариант конфига по шаблону (`broken_nested_regex_detected`) и отдаёт ассеты напрямую, пока на сервере не выполнен `nginx_sync.php`. Также починён порядок в генераторе vhost: список self-signed доменов теперь вычисляется до использования в Cloudflare-блоке. **На работающем nginx-сервере нужно один раз выполнить `sudo php /var/www/orbitra/cli/nginx_sync.php`.**

## 🆕 Новое в v1.1.6

- **Выбор режима SSL в «Доменах»** — три режима на домен: Let's Encrypt (автовыпуск), Cloudflare (прокси; генерируемый vhost восстанавливает реальный IP посетителя из диапазонов Cloudflare IPv4+IPv6 и определяет HTTPS по `CF-Visitor`), свой сертификат (пути к cert+ключу). Строки UI на всех 7 языках.
- **Smoke-тесты установки и диагностика** — `install.sh` после установки проверяет наличие nginx-локации `_internal_assets`, записываемость ACME-webroot, наличие self-signed сертификата и синтаксис конфига nginx; `cli/check_landings.php` диагностирует права на директории landings/ и offers/, полноту конфига nginx, доступность ACME-webroot, наличие SSL-сертификатов и отдачу тестового ассета.
- **Гарантированная загрузка ассетов лендингов/офферов** — HTML перед вставкой base-тега переписывается: абсолютные пути ассетов (`/css/style.css`) становятся относительными (`./css/style.css`), JS-полифилл сохраняет плавную прокрутку по якорям под base-тегом. Referer-фолбэк распознаёт URL кампаний (`/bd86o7dw`), разрешая лендинг/оффер по настройкам потоков. При отсутствии nginx-локации `/_internal_assets/` включается фолбэк: ассет отдаётся напрямую из PHP с поддержкой Range-запросов (206 Partial Content).
- **Удалено** — массовой импорт .txt/.csv (кнопки в Кампаниях, Офферах, Лендингах и Источниках) убран намеренно.

## 🆕 Новое в v1.1.5

- **Управление и проверка SSL (ORB-014)** — `core/ssl_manager.php` проверяет покрытие сертификатом для каждого домена; сгенерированный vhost nginx получает HTTPS-блок с self-signed сертификатом для доменов без Let's Encrypt и Cloudflare; настройка Cloudflare Full (Strict) описана в `docs/CLOUDFLARE_FULL_STRICT_SSL.md`; форма vhost зафиксирована регрессионным тестом на 279 проверок (`tests/nginx_config_regression_test.php`). **На работающем nginx-сервере нужно один раз выполнить `sudo php /var/www/orbitra/cli/nginx_sync.php`**.
- **Свои SSL-сертификаты для доменов** — загрузка сертификата и ключа в настройках домена (UI «Домены», все 7 локалей).
- **SUBID в логе трафика** — значения SUBID читаются из параметров клика на пути клика и в LeadForge; тесты покрывают отсутствующий ключ, битый JSON и NULL.
- **Массовая загрузка файлов** — общий компонент `BulkFileUpload` с разбором CSV и ошибками по каждому файлу, подключён в Bot Settings, «Персонализации», Кампаниях, Лендингах, Офферах и Источниках; инспектор `cli/check_landings.php`.
- **Прочее** — переработан контроль доступа по IP (`core/ip_access.php`); фронтенд-бандл пересобран — UI SSL и массовой загрузки, закоммиченные без пересборки, наконец едет в дисте.

## 🆕 Новое в v1.1.4

- **Сниппеты трекинга переведены на английский** — код-блоки во вкладке «Метод подключения» редактора кампаний (KClient JS/PHP, скрипт отслеживания, баннерные блоки, пиксели клика и конверсии, countdown / back-button / exit-intent, WordPress-шорткоды) несли хардкодные русские комментарии прямо в шаблонах — независимо от языка панели. Теперь все комментарии шаблонов на английском, переведены по месту (намеренно без локале-ключей: это код, который пользователь вставляет на свой сайт). Единственная оставшаяся русская строка — намеренная: `text_ru="Купить"` в примере WordPress-шорткода демонстрирует сам параметр мультиязычности.

## 🆕 Новое в v1.1.3

- **Восемь палитрных тем** — четыре цветовые схемы, каждая в светлой и тёмной вариации, выбираются в «Персонализации»: Кобальт (сигнальный синий на белом и чистом чёрном), Канарейка (чёрные кнопки на белом; канареечный жёлтый на графите), Пергамент (тёплый кремовый фон с чернильными кнопками; чернильная тёмная с кремовыми поверхностями), Индиго (сине-фиолетовая на светлой канве и глубоком индиго). Палитры портированы из опубликованных дизайн-анализов под нейтральными цветовыми именами — брендовые названия и шрифты в продукт не входят.
- **Хардкодные серые заменены на переменные темы** — остатки `bg-white` / `gray-*` в «Автоматизации», статусе администратора и вкладке трекинга кампании используют `var(--color-*)`, поэтому любая тема, включая новые тёмные палитры, красит эти страницы корректно. Вкладка трекинга заодно ужата: панель «Настройки и опции» показывается только для методов с опциями, а блок сгенерированного кода стал полной ширины с компактной кнопкой копирования в заголовке.
- **Фиксы** — задвоенный «+ +» на кнопке «Подключить Cost Sync» (литеральный плюс в строке перевода рядом с иконкой); починен бандл страницы Conversion Types, сломанный с 1.1.2, — блок немапленных статусов из релизных нот 1.1.2 реально доехал до пользователей только сейчас.

## 🆕 Новое в v1.1.2

- **Лог входящих постбэков (ORB-001)** — каждый постбэк, приходящий в трекер, записывается как есть, до маппинга статусов и атрибуции. Пропавшая конверсия или конверсия с «не тем» статусом теперь прослеживается до конкретного запроса, который прислала сеть.
- **Немапленные статусы конверсий + ретроактивный маппинг** — движки Facebook и TikTok сначала смотрят кастомный маппинг статусов и только потом дефолтный; статус, для которого нет правила, сохраняется как unmapped, а не приводится к догадке. Новый блок в настройках Conversion Types показывает накопленные немапленные статусы и позволяет задать правило — оно применяется и задним числом, переклассифицируя уже сохранённые конверсии.
- **LeadForge больше не выдумывает subid (ORB-011)** — убран фолбэк `bin2hex(random_bytes(8))`, выдумывавший subid для лидов без контекста клика. Subid проверяется по таблице `clicks`: просроченный или отсутствующий — лид отклоняется с нейтральным сообщением для покупателя и записью в `system_logs`; при недоступной БД лид всё равно принимается, чтобы доступность не зависела от проверки.
- **Консолидация роутинга** — `router.php` удалён, `index.php` — единственный фронт-контроллер; в него перенесены оба guard'а: Disabled Domain (404 для выключенных доменов) и Admin Access (ограничение админских маршрутов по настройке домена). Маршрут постбэков и пиксель конверсий работают через него же, отдают валидный GIF с корректными кодами ошибок и покрыты real-HTTP-тестами (ORB-010).
- **Ассеты лендингов через X-Accel-Redirect (ORB-013)** — PHP проверяет путь к ассету и отдаёт файл nginx'у через `X-Accel-Redirect`: файл уходит sendfile'ом (zero-copy), PHP освобождается для следующего запроса — лендинг с 30 ассетами больше не занимает 30 PHP-воркеров. Внутренняя локация отдаёт только типы из белого списка, остальное (включая `.php`) — `deny all`. **На работающем nginx-сервере нужно один раз выполнить `sudo php /var/www/orbitra/cli/nginx_sync.php`** — половина изменения живёт в конфиге vhost. Apache-установкам ничего ручного не нужно.
- **Производительность клика и аналитики** — синхронные обращения к внешним geo-API убраны из пути клика (клик не ждёт сторонний ответ); на таблицу `clicks` добавлены покрывающие индексы под фильтры аналитики и трендов.
- **Фиксы** — редирект-луп за Cloudflare Flexible SSL (`orbitraIsHttps()` читает `CF-Visitor`); единый источник public IP сервера (ORB-005) вместо разрозненных проверок в каждой фиче; фрагмент-фикс в IntegrationsPage.

## 🆕 Новое в v1.1.1

- **POST формы локального оффера больше не отдаёт 404** — загруженный оффер отдаётся inline по адресу кампании (`/pr6sxv41`), поэтому браузер разрешал `action="order.php"` относительно корня домена и отправлял лид на `/order.php`. Этот путь первым забирал nginx: `snippets/fastcgi-php.conf` заканчивается на `try_files $fastcgi_script_name =404`, файла `order.php` в корне нет — 404 отдавал сам веб-сервер, и order-мост в `index.php` не запускался. Генератор конфига (`core/nginx_config.php`) и базовый конфиг из `install.sh` теперь передают `/order.php`, `/offers/<id>/*.php` и `/lander/<slug>/*.php` во фронт-контроллер. **На работающем сервере нужно один раз выполнить `sudo php /var/www/orbitra/cli/nginx_sync.php`** — половина этого исправления лежит в конфиге nginx, а не в коде.
- **`success.php` добавлен в список обработчиков** — сгенерированный `order.php` заканчивается относительным `Location: success.php`, поэтому лид мог быть принят партнёркой, а покупатель шагом позже всё равно получал 404. `orbitraBundleHandlers()` — единый список для всех трёх мостов: `order.php`, `thank_you.php`, `success.php`, `send.php`, `lucky.php`, `lemon.php`, плюс `api.php` только на маршрутах, где id бандла есть в самом URL, и никогда в корне домена, где это админский API трекера.
- **Action формы указывает на адрес самого оффера** — относительный `*.php` в отданном оффере становится `/offers/<id>/order.php`: POST лида несёт id оффера, а не полагается на cookie или Referer, и отправщик `api.php` из бандла Ezaff больше не конфликтует с `/api.php`. Анкоры `#order`, ассеты и любые абсолютные или внешние action не трогаются — намеренно без тега `<base>`, который превратил бы каждую кнопку «#order» в переход с адреса кампании.
- **Загруженный PHP больше не исполняется напрямую с диска** — `/offers/<id>/order.php` раньше уходил прямо в PHP-FPM, то есть файл из загруженного архива выполнялся в обход переключателя «Allow PHP landings» и лимита времени. Оба маршрута бандлов идут через `index.php`, а `/landings/<id>/*.php` (директория хранения за `/lander/<slug>/`, не публичный маршрут) отдаёт 404.
- **`ORBITRA_OFFER_ID` / `ORBITRA_OFFER_URL` / `ORBITRA_OFFER_PATH`** — объявляются до запуска любого собственного PHP локального оффера, на всех трёх путях его исполнения. Бандл может написать `defined('ORBITRA_OFFER_URL') ? ORBITRA_OFFER_URL . 'order.php' : 'order.php'` и остаться работоспособным вне Orbitra.
- **`tests/lander_order_route_test.php` вырос до 50 проверок** — `success.php` на обоих мостах, константы контекста оффера, `/api.php` никогда не перехватывается бандлом, двенадцать случаев перезаписи action и сверка того, что генератор vhost и `install.sh` описывают маршруты бандлов одинаково и ставят их перед общим PHP-обработчиком.

## 🆕 Новое в v1.1.0

- **Атрибуция конверсий из постбеков партнёрок** — конверсия, принятая через `postback.php`, теперь получает измерения своего клика: `campaign_id`, `offer_id`, `sub_id_1..5`, IP и user agent. Раньше заполнялся только `click_id`, поэтому журнал конверсий показывал строки без кампании и оффера, а фильтры по кампании/офферу в нём не находили ничего. Логика вынесена в `core/ConversionAttribution.php` и переиспользуется импортом конверсий из CSV.
- **Восстановлены слоистые отчёты** — в SQL-запросе `campaign_report` оказался комментарий вида `//`, которого SQLite не понимает (там допустимы только `--` и `/* */`). Запрос не парсился целиком, поэтому **любой** сгруппированный отчёт (Sub1…Sub30, Страна, День, Кампания, Оффер) отдавал ошибку вместо строк.
- **Регистронезависимое сопоставление статусов** — `Approved` или `PENDING` от партнёрки записывались как конверсия, не попадающая ни в одну группу статусов: в кампании было видно `Конверсии: 1` при нулевых Продажах, Лидах, Отклонённых и Трэше. Сравнение приведено к нижнему регистру и в `mapStatus()`, и в агрегатах отчётов; словарь дополнен значениями `approve/accepted/paid`, `new/wait/waiting/processing`, `reject/decline/cancelled` и `spam/duplicate`.
- **`subid` не попадает в измерение Sub1** — входящий `subid` это Click ID трекера (Dr. Cash передаёт его в `&sub1={subid}`), а sub-измерения конверсии берутся из `parameters_json` самого клика. Иначе каждая строка отчёта по Sub1 стала бы уникальной для одного клика.
- **Приоритет собственного правила статуса** — при одновременных `trash_status=trash` и `rejected_status=rejected,trash` статус `trash` остаётся Трэшем, а не уходит тому типу, который просто упомянул его первым.
- **Миграция 33** — дозаполняет `campaign_id`, `offer_id`, `sub_id_1..5`, IP и user agent у ранее записанных конверсий по их кликам. Строки, у которых клик уже удалён, не трогаются.
- **Мониторинг сбоев конверсий** — `core/ConversionMonitor.php` пишет причину, по которой конверсию не удалось создать (неизвестный клик, ошибка БД), в `var/logs/conversion_failures.log`; `api.php?action=conversion_monitoring` отдаёт количество и долю сбоев за окно, а `conversion_monitor_cron.php` (раз в 5–15 минут) шлёт оповещение в Telegram при превышении порога.
- **Выпуск SSL с учётом облака** — `core/CloudDetector.php` определяет домены за прокси Cloudflare по диапазонам IP и заголовкам ответа, чтобы не гонять Certbot туда, где он не пройдёт валидацию; `core/ssl_manager.php` проверяет DNS и passwordless sudo до запроса сертификата, а в «Доменах» появился перевыпуск с понятной причиной отказа. Подробности — в `CERTBOT_SETUP.md` и `SECURITY_OPERATIONS_CHECKLIST.md`.
- **Возвращена проверка TLS на исходящих запросах** — `telegram_notify.php`, `telegram_bot.php`, `postback_queue_cron.php` и `core/LeadForge.php` отправляли cURL-запросы с `CURLOPT_SSL_VERIFYPEER => false` и принимали любой сертификат. Проверка снова включена по умолчанию и ослабляется только при явном локальном окружении (`APP_ENV=local`, `ORBITRA_ENV=dev`, `ORBITRA_SKIP_SSL_VERIFY=1`).
- **Подключение расходов TikTok под API v1.3** — запрос `advertiser/info/` с массивом `advertiser_ids`, разбор Advertiser ID строго из цифр (вычищаются типографские кавычки, невидимые символы и пробелы из буфера обмена) и ошибки с указанием причины вместо голого кода. В подписи к полю токена указано, что нужен токен **Marketing API** с правами Ads Management / Reporting.
- **Руководство по 1-Click OAuth для Google Ads** — пошаговая настройка проекта Cloud, Redirect URI и Developer Token прямо в панели, CLI-проверка `check_google_ads_oauth.php` и описание переменных в `.env.example`.
- **Регрессионный тест `tests/postback_attribution_test.php`** — путь Dr. Cash целиком: атрибуция, повторный постбек без перезаписи, бэкфилл, принадлежность статуса ровно одной группе, подсчёт статусов в разном регистре и строка отчёта по Sub1 с кликами и конверсиями вместе.

## 🆕 Новое в v1.0.9

- **Универсальное разрешение макросов в локальных PHP-лендингах и офферах** — перехват буфера вывода (`ob_start()`) с автоматической подстановкой всех макросов (`{subid}`, `{sub1}`, `{click_id}`, `{{subid}}`, `{data1}`, `{external_id}` и др.) перед отдачей клиенту, установка сквозных cookie `orbitra_click`, `orbitra_subid`, `subid`, `orbitra_lo`.
- **Отказоустойчивая обработка лидов в `order.php`** — многоуровневый каскад извлечения идентификатора клика (куки, сессии, параметры URL, сгенерированный ID), гарантирующий корректную отправку лидов в CPA-сети даже при отправке непрорезолвленного макроса.

**Схемы потоков:**

- **Landing + Offer** — показ лендинга со ссылкой на оффер (оффер опционален)
- **Action** — выполнение действия (404, 200 OK, etc.)
- **Cloak** — cloaking: подозрительным посетителям (боты, модераторы, дата-центр/VPN) показывается белая страница, реальным людям — денежная (см. ниже «Cloaking»)

### 🔀 Типы редиректа (с версии 0.9.6.0)

Каждый оффер имеет поле `redirect_type`, которое определяет, **как именно** посетитель отправляется к URL оффера. До 0.9.6.0 это поле хранилось, но в рантайме всегда отдавался HTTP 302. Теперь поддерживается:

| Тип | Поведение | Когда использовать |
|---|---|---|
| `redirect` | HTTP 302 (по умолчанию) | Большинство случаев — быстро и прозрачно |
| `js` | HTML со `<script>window.location` | Обходит блокировки серверного редиректа, сохраняет referrer |
| `meta_refresh` | `<meta http-equiv="refresh">` | Максимальная совместимость со старыми браузерами |
| `frame`/`iframe` | Оффер в полноэкранном `<iframe>` | Посетитель остаётся на вашем домене |
| `form_submit` | Авто-сабмит POST-формы | Данные трекинга в теле запроса, а не в URL |
| `curl_proxy` | Удалённая страница через ваш сервер + `<base>` | Контент под вашим доменом |

Макросы `{clickid}`, `{offer_id}`, `{sub_id_1..30}` и SSRF-проверка применяются ко всем типам одинаково.

### 🕵️ Cloaking (с версии 0.9.6.0)

Схема потока **Cloak** разделяет трафик на две ветки:

- **Safe page (белая)** — для ботов, модераторов, дата-центров/VPN. Настраивается: лендинг, URL или встроенный HTML.
- **Money page (денежная)** — для реальных людей. Работает как схема «Лендинг + Оффер».

**Слои определения** (`core/CloakDetector.php`):
- **Datacenter/hosting** — совпадение ASN по списку `core/data/asn_blocklist.json` (AWS/GCP/Azure/Hetzner/OVH и др.) + ключевые слова в ISP.
- **VPN/proxy** — список известных VPN-ASN.
- **Боты** — переиспользует существующие таблицы `bot_ips`/`bot_signatures`.
- **UA-эвристики** — отсутствие User-Agent, curl/python/headless/googlebot и т.п., отсутствие `Accept-Language`.
- **JS-проверка (опционально, по умолчанию выключена)** — активный слой. Посетитель сначала получает белую страницу и переходит на денежную только после выполнения JavaScript по одноразовой ссылке с HMAC-подписью и TTL 5 минут. Явный `navigator.webdriver=true` остаётся на белой странице. Ограничения приватности, пустой список плагинов, canvas и фоновые вкладки не считаются бот-сигналами, потому что они встречаются у обычных пользователей. Всё, что не исполняет JS, остаётся на белой странице. Цена — один дополнительный переход для каждого живого посетителя, поэтому слой включается отдельным флажком.

**Чувствительность** — сигналы делятся на «жёсткие» (попадание в блок-лист ASN/ботов, отсутствие UA, UA краулера или консольной утилиты) и «мягкие» (hosting-ключевое слово в ISP, отсутствие `Accept-Language`):

| Уровень | Срабатывает |
|---|---|
| **Low** | только жёсткий сигнал |
| **Medium** (по умолчанию) | жёсткий сигнал или два мягких |
| **High** | любой одиночный сигнал |

Список ASN редактируется вручную в `core/data/asn_blocklist.json`.

### Локальные лендинги: загрузка ZIP и пути к файлам

Архив распаковывается в `landings/<ID лендинга>/`, точкой входа считается `index.html` (или `index.php`, если файл положен на сервер вручную — в загружаемом ZIP PHP запрещён). Сама страница отдаётся по URL кампании, а не по `/landings/<ID>/`, поэтому относительные пути внутри лендинга браузер запрашивает от корня домена.

С версии 0.9.6.2 трекер разбирает такие запросы сам: он помнит показанный лендинг (cookie `orbitra_lp`) и отдаёт файл из его папки. Правки в разметке не нужны — архив, который открывается локально двойным кликом, работает в трекере как есть. Поддержаны относительные пути, `srcset`, `url()` внутри стилей, байтовые диапазоны для `<video>`, `ETag`/`304` и кеширование.

Что стоит знать:

- Абсолютные пути (`/img/hero.jpg`) и относительные (`img/hero.jpg`) работают одинаково.
- Ссылки на внешние домены остаются как есть — трекер их не проксирует.
- Отдаются только медиа и статика по списку расширений; `.php`, `.htaccess` и прочее из папки лендинга наружу не уходит.
- При повторной загрузке архива в тот же лендинг ID сохраняется, кеш в браузере живёт час.

### Ссылка на оффер: макрос `{offer}` (с версии 0.9.6.4)

Самый простой способ — оформить кнопку макросом, как в Keitaro:

```html
<a href="{offer}">Купить</a>
```

Трекер подставит вместо `{offer}` URL оффера, который выбрал поток, — уже с `{clickid}` и остальными параметрами внутри.

**Если офферов на странице несколько**, выбор должен идти через трекер, а не дописыванием параметра к `{offer}`:

```html
<a href="/?_lp=1&offer_id=10">Оффер 10</a>
<a href="/?_lp=1&offer_id=22">Оффер 22</a>
```

`{offer}` разворачивается в прямую ссылку рекламодателя, поэтому `{offer}&offer_id=10` просто допишет лишний параметр к чужому URL и оффер не переключит. По `/?_lp=1&offer_id=N` трекер выберет нужный оффер и перезапишет `offer_id` у клика, чтобы конверсия легла на него.

В HTML локального лендинга подставляются: `{offer}`, `{offer_id}`, `{clickid}`, `{subid}`, а также все параметры клика — `{keyword}`, `{sub_id_1}` … `{sub_id_30}` и прочие, пойманные шаблоном источника. Значения из URL экранируются, поэтому чужой параметр не сможет вставить свой тег.

Ничего, кроме этих макросов, трекер не трогает: `{unknown}`, JS-шаблоны, синтаксис Vue и Angular остаются как есть.

Если в потоке нет оффера, `{offer}` превращается в `/?_lp=1` — по клику будет понятное сообщение, а не пустая ссылка.

> В лендинге на PHP (`index.php`) макросы не накладываются — там доступны переменные `$clickId` и `$offerUrlMacros`.

### Переход с лендинга на оффер (`/?_lp=1`)

Для локальных лендингов в схеме «Лендинг + Оффер» переход на оффер делается ссылкой `/?_lp=1` (совместимо с Keitaro). Оформите кнопку оффера на странице лендинга так:

```html
<a href="/?_lp=1">Перейти к офферу</a>
```

При клике трекер находит оффер, привязанный к клику посетителя (запоминается через cookie при показе лендинга), подставляет макросы (`{clickid}`, `{sub_id_1}` … `{sub_id_30}`, `{offer_id}` и др.) и делает редирект на оффер. Чтобы указать конкретный оффер из потока, добавьте его ID:

```html
<a href="/?_lp=1&offer_id=10">Оффер 10</a>
```

Если в потоке выбран только лендинг без оффера, лендинг открывается как финальная страница, а ссылка `/?_lp=1` ничего не делает (оффера нет).

## 🔗 Click API с токенами

### Что такое Click API?

Click API — это механизм для работы с интеграционными скриптами, когда вместо `campaign_id` используется уникальный токен кампании.

### Преимущества токенов
- **Совместимость с Keitaro** — существующие скрипты продолжат работать
- **Безопасность** — токен сложно угадать, ID легко перебрать
- **Гибкость** — можно менять кампании без изменения скриптов

### Как это работает

**Традиционный подход:**
```
https://tracker.com/click.php?campaign_id=123
```

**С токеном:**
```
https://tracker.com/click.php?token=abc123def456...
```

### Генерация токена

- **Длина**: 32 символа (hex)
- **Уникальность**: автоматическая генерация при создании кампании
- **Регенерация**: можно сгенерировать новый токен в редакторе

### Сохранение токенов при миграции

При импорте из Keitaro:
1. Токены из Keitaro автоматически переносятся в Orbitra
2. Сохраняется полная совместимость с существующими интеграциями
3. Интеграционные скрипты продолжат работать без изменений

### Где используется токен

- **Интеграционные скрипты** на лендингах
- **API запросы** от сторонних систем
- **Постбеки** от партнерских сетей
- **Вебхуки** от внешних сервисов

### Подготовка дампа Keitaro

На сервере Keitaro выполните:

```bash
# 1. Подключитесь к Keitaro серверу
ssh root@YOUR_KEITARO_SERVER_IP

# 2. Создайте дамп настроек (без логов кликов)
bash -lc '
source /etc/keitaro/env/inventory.env

# Конфиг для подключения к БД
cat > /root/keitaro-mariadb.cnf <<EOF
[client]
user=$MARIADB_KEITARO_USER
password=$MARIADB_KEITARO_PASSWORD
host=127.0.0.1
port=3306
protocol=tcp
EOF
chmod 600 /root/keitaro-mariadb.cnf

# Создание дампа таблиц
TABLES="keitaro_affiliate_networks keitaro_groups keitaro_offers keitaro_domains keitaro_campaigns keitaro_campaign_postbacks keitaro_landings keitaro_streams keitaro_stream_filters keitaro_stream_offer_associations keitaro_stream_landing_associations keitaro_traffic_sources keitaro_ref_sources"

mysqldump --defaults-extra-file=/root/keitaro-mariadb.cnf \
  --single-transaction --quick --skip-lock-tables \
  "$MARIADB_KEITARO_DATABASE" $TABLES \
  | gzip > /root/keitaro_orbitra_full.sql.gz

ls -lah /root/keitaro_orbitra_full.sql.gz
'

# 3. Скачайте файл к себе
scp root@YOUR_KEITARO_SERVER_IP:/root/keitaro_orbitra_full.sql.gz .
```

### Импорт в Orbitra

1. Откройте **Миграции** в меню админки
2. Следуйте инструкции в блоке "Как создать бекап Keitaro"
3. Загрузите файл `keitaro_orbitra_full.sql.gz`
4. Выберите что импортировать:
   - ☑ Партнёрки (affiliate networks)
   - ☑ Офферы
   - ☑ Домены
   - ☑ Кампании
   - ☑ Потоки (streams)
   - ☑ Постбеки кампаний
   - ☑ Лендинги
   - ☑ Источники трафика
5. Нажмите **"Показать предпросмотр"** для проверки
6. Нажмите **"Импортировать в Orbitra"** для реального импорта

### Что импортируется

| Сущность Keitaro | Таблица Orbitra | Особенности |
|------------------|-----------------|-------------|
| `keitaro_affiliate_networks` | `affiliate_networks` | Сохраняются postback URL |
| `keitaro_offers` | `offers` | Сохраняются URL, payout, geo |
| `keitaro_domains` | `domains` | Сохраняется парковка, HTTPS |
| `keitaro_campaigns` | `campaigns` | **Сохраняются токены!** |
| `keitaro_streams` | `streams` | Сохраняются фильтры, схемы |
| `keitaro_landings` | `landings` | Сохраняются названия |
| `keitaro_traffic_sources` | `traffic_sources` | Сохраняются параметры |
| `keitaro_ref_sources` | — | Используется в streams |

### Особенности миграции

- **Токены сохраняются** — ваши скрипты продолжат работать
- **Streams filters** — фильтры конвертируются в новый формат
- **Postbacks** — S2S постбеки переносятся автоматически

## ♻️ Очередь S2S-постбеков с retry (с версии 0.9.6.0)

До 0.9.6.0 исходящие S2S-постбеки отправлялись синхронно прямо во время обработки входящего постбека (`fire-and-forget`): если эндпоинт партнёрки был недоступен, постбек терялся безвозвратно. Теперь постбеки доставляются надёжно.

**Как работает:**
1. При входящем постбеке (`postback.php`) каждая исходящая доставка добавляется в таблицу `s2s_postbacks_log` со `status='pending'` и макро-подставленным URL.
2. Воркер `postback_queue_cron.php` (запускается по cron каждую минуту) выбирает «должные» строки, выполняет HTTP-запрос и пишет результат.
3. Критерий успеха — HTTP `2xx-399`. Иначе — повтор с экспоненциальным backoff: **60с → 5м → 30м → 2ч → 24ч**. Всего 6 попыток (1 первая + 5 повторов), после чего строка помечается `status='failed'` (видна в логах S2S).
4. SSRF-проверка выполняется дважды: при постановке в очередь и перед отправкой. Хост, который резолвится в приватный/зарезервированный адрес, помечается `failed` без повторов; неудачный DNS считается временной ошибкой и уходит в повтор.
5. Строку, взятую в работу (`status='in_flight'`) и брошенную упавшим воркером, следующий запуск возвращает в очередь через 10 минут — иначе она была бы невидима для выборки, которая смотрит только на `pending`.

> ⚠️ **Без установленного крона очередь не разбирается и постбеки не уходят.** Это первое, что нужно сделать после обновления на 0.9.6.0.

**Установка воркера:** **Настройки → Автоматизация → Очередь постбеков**, кнопка «Установить cron доставки» — действие `postback_queue_install_user_cron` (ставит строку `* * * * *` в crontab пользователя). Удаление — `postback_queue_remove_user_cron`. Состояние воркера (last ping, processed/delivered/requeued/failed за последний запуск, счётчики по статусам) отдаёт `postback_queue_info` и показывает та же панель.

**Расширенные макросы** (раньше было 6, теперь поддерживаются все): `{subid}`, `{status}`, `{payout}`, `{currency}`, `{external_id}`, `{tid}`, `{campaign_id}`, `{cost}`, `{revenue}`, `{profit}`, `{sub_id_1}` … `{sub_id_30}`.

**Исправленный баг POST:** постбеки с методом POST теперь отправляют тело (раньше уходил пустой POST). Поля из query-string переносятся в `CURLOPT_POSTFIELDS` с `Content-Type: application/x-www-form-urlencoded`.

## 💰 Автоимпорт расходов из Facebook Ads / Google Ads (с версии 0.9.6.0)

Два новых engine агрегатора забирают дневной рекламный расход и атрибутируют его к кликам, так что отчёты ROI/прибыли больше не показывают нулевой расход.

**Engines** (в `aggregator_engines/`):
- **FacebookAdsEngine** — Facebook Marketing API `/act_<id>/insights`. Авторизация: long-lived User Access Token или System User Token + Ad Account ID.
- **GoogleAdsEngine** — Google Ads API (REST, v19, GAQL). Авторизация server-to-server OAuth2: `developer_token` + `client_id` + `client_secret` + `refresh_token` + `customer_id`. `refresh_token` не протекает; короткоживущий `access_token` получается автоматически и кешируется в таблице `oauth_tokens`.

**Атрибуция к кликам:** импортированный расход (таблица `cost_records`) распределяется по кликам через `UPDATE clicks SET cost = cost + ?`, группируя по дню и рекламному ID. Ключи join — `json_extract(clicks.parameters_json, '$.ad_id')` → `$.campaign_id` → `$.campaignid` (для ValueTrack), те самые ID, которые уже проставляются встроенными traffic-source-шаблонами Facebook и Google Ads.

**Настройка:** Администрирование → Агрегатор → новый connection с engine `facebook` или `google_ads`, поля форм генерируются динамически через `getRequiredFields()`. Тест подключения — кнопкой «Test Connection». Синхронизация — по cron (`aggregator_cron.php`) или вручную (кнопка Sync).
