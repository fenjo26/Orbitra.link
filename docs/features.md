# Основные Функции Orbitra v1.0.1

Полный обзор функциональности трекера Orbitra — современного аналога Keitaro Tracker.

## 🆕 Новое в v1.0.1

- **1-Click TikTok For Business** — OAuth-вход попапом из Pixel Vault (api.php `tiktok_oauth_start/callback/connect_accounts`, зеркало Facebook-флоу): авто-обнаружение кабинетов (`/oauth2/advertiser/get/`) и пикселей (`/pixel/list/`), чекбоксы кабинетов с интервалом синка расходов (движок `tiktok`), авто-импорт пикселей в хранилище; токен не покидает сервер (во попапе только flow_id).

### Потоки (Streams)

**3 типа потоков:**
1. **Intercept** — перехват (высший приоритет, для особых случаев)
2. **Regular** — обычный поток (основной трафик)
3. **Fallback** — замыкающий (резервный поток)

**Фильтры потоков:**
- **Страна** — выбор стран (включая профили: EU, CIS, Americas)
- **Устройство** — desktop, mobile, tablet
- **ОС** — Windows, macOS, Linux, Android, iOS
- **Браузер** — Chrome, Safari, Firefox, Edge, Opera
- **ISP** — провайдер (регулярка)
- **IP** — белый/черный список
- **Keyword** — ключевые слова
- **Referer** — реферер (регулярка)
- **Время** — часы работы
- **День недели** — дни недели

**Схемы потоков:**
- **URL** — редирект на внешний URL
- **Offer** — редирект на оффер
- **Landing** — показ локального лендинга
- **Landing + Offer** — показ лендинга со ссылкой на оффер (оффер опционален)
- **Action** — выполнение действия (404, 200 OK, etc.)
- **Cloak** — cloaking: подозрительным посетителям (боты, модераторы, дата-центр/VPN) показывается белая страница, реальным людям — денежная (см. ниже «Cloaking»)

### 🔀 Типы редиректа (с версии 0.9.6.0)

Каждый оффер имеет поле `redirect_type`, которое определяет, **как именно** посетитель отправляется к URL оффера. До 0.9.6.0 это поле хранилось, но в рантайме всегда отдавался HTTP 302. Теперь поддерживается:

| Тип | Поведение | Когда использовать |
|---|---|---|
| `redirect` | HTTP 302 (по умолчанию) | Большинство случаев — быстро и прозрачно |
| `js` | HTML со `<script>window.location` | Обходит блокировки серверного редиректа, сохраняет referrer |
| `meta_refresh` | `<meta http-equiv="refresh">` | Максимальная совместимость со старыми браузерами |
| `frame`/`iframe` | Оффер в полноэкранном `<iframe>` | Посетитель остаётся на вашем домене |
| `form_submit` | Авто-сабмит POST-формы | Данные трекинга в теле запроса, а не в URL |
| `curl_proxy` | Удалённая страница через ваш сервер + `<base>` | Контент под вашим доменом |

Макросы `{clickid}`, `{offer_id}`, `{sub_id_1..30}` и SSRF-проверка применяются ко всем типам одинаково.

### 🕵️ Cloaking (с версии 0.9.6.0)

Схема потока **Cloak** разделяет трафик на две ветки:

- **Safe page (белая)** — для ботов, модераторов, дата-центров/VPN. Настраивается: лендинг, URL или встроенный HTML.
- **Money page (денежная)** — для реальных людей. Работает как схема «Лендинг + Оффер».

**Слои определения** (`core/CloakDetector.php`):
- **Datacenter/hosting** — совпадение ASN по списку `core/data/asn_blocklist.json` (AWS/GCP/Azure/Hetzner/OVH и др.) + ключевые слова в ISP.
- **VPN/proxy** — список известных VPN-ASN.
- **Боты** — переиспользует существующие таблицы `bot_ips`/`bot_signatures`.
- **UA-эвристики** — отсутствие User-Agent, curl/python/headless/googlebot и т.п., отсутствие `Accept-Language`.
- **JS-проверка (опционально, по умолчанию выключена)** — активный слой. Посетитель сначала получает белую страницу и переходит на денежную только после выполнения JavaScript по одноразовой ссылке с HMAC-подписью и TTL 5 минут. Явный `navigator.webdriver=true` остаётся на белой странице. Ограничения приватности, пустой список плагинов, canvas и фоновые вкладки не считаются бот-сигналами, потому что они встречаются у обычных пользователей. Всё, что не исполняет JS, остаётся на белой странице. Цена — один дополнительный переход для каждого живого посетителя, поэтому слой включается отдельным флажком.

**Чувствительность** — сигналы делятся на «жёсткие» (попадание в блок-лист ASN/ботов, отсутствие UA, UA краулера или консольной утилиты) и «мягкие» (hosting-ключевое слово в ISP, отсутствие `Accept-Language`):

| Уровень | Срабатывает |
|---|---|
| **Low** | только жёсткий сигнал |
| **Medium** (по умолчанию) | жёсткий сигнал или два мягких |
| **High** | любой одиночный сигнал |

Список ASN редактируется вручную в `core/data/asn_blocklist.json`.

### Локальные лендинги: загрузка ZIP и пути к файлам

Архив распаковывается в `landings/<ID лендинга>/`, точкой входа считается `index.html` (или `index.php`, если файл положен на сервер вручную — в загружаемом ZIP PHP запрещён). Сама страница отдаётся по URL кампании, а не по `/landings/<ID>/`, поэтому относительные пути внутри лендинга браузер запрашивает от корня домена.

С версии 0.9.6.2 трекер разбирает такие запросы сам: он помнит показанный лендинг (cookie `orbitra_lp`) и отдаёт файл из его папки. Правки в разметке не нужны — архив, который открывается локально двойным кликом, работает в трекере как есть. Поддержаны относительные пути, `srcset`, `url()` внутри стилей, байтовые диапазоны для `<video>`, `ETag`/`304` и кеширование.

Что стоит знать:

- Абсолютные пути (`/img/hero.jpg`) и относительные (`img/hero.jpg`) работают одинаково.
- Ссылки на внешние домены остаются как есть — трекер их не проксирует.
- Отдаются только медиа и статика по списку расширений; `.php`, `.htaccess` и прочее из папки лендинга наружу не уходит.
- При повторной загрузке архива в тот же лендинг ID сохраняется, кеш в браузере живёт час.

### Ссылка на оффер: макрос `{offer}` (с версии 0.9.6.4)

Самый простой способ — оформить кнопку макросом, как в Keitaro:

```html
<a href="{offer}">Купить</a>
```

Трекер подставит вместо `{offer}` URL оффера, который выбрал поток, — уже с `{clickid}` и остальными параметрами внутри.

**Если офферов на странице несколько**, выбор должен идти через трекер, а не дописыванием параметра к `{offer}`:

```html
<a href="/?_lp=1&offer_id=10">Оффер 10</a>
<a href="/?_lp=1&offer_id=22">Оффер 22</a>
```

`{offer}` разворачивается в прямую ссылку рекламодателя, поэтому `{offer}&offer_id=10` просто допишет лишний параметр к чужому URL и оффер не переключит. По `/?_lp=1&offer_id=N` трекер выберет нужный оффер и перезапишет `offer_id` у клика, чтобы конверсия легла на него.

В HTML локального лендинга подставляются: `{offer}`, `{offer_id}`, `{clickid}`, `{subid}`, а также все параметры клика — `{keyword}`, `{sub_id_1}` … `{sub_id_30}` и прочие, пойманные шаблоном источника. Значения из URL экранируются, поэтому чужой параметр не сможет вставить свой тег.

Ничего, кроме этих макросов, трекер не трогает: `{unknown}`, JS-шаблоны, синтаксис Vue и Angular остаются как есть.

Если в потоке нет оффера, `{offer}` превращается в `/?_lp=1` — по клику будет понятное сообщение, а не пустая ссылка.

> В лендинге на PHP (`index.php`) макросы не накладываются — там доступны переменные `$clickId` и `$offerUrlMacros`.

### Переход с лендинга на оффер (`/?_lp=1`)

Для локальных лендингов в схеме «Лендинг + Оффер» переход на оффер делается ссылкой `/?_lp=1` (совместимо с Keitaro). Оформите кнопку оффера на странице лендинга так:

```html
<a href="/?_lp=1">Перейти к офферу</a>
```

При клике трекер находит оффер, привязанный к клику посетителя (запоминается через cookie при показе лендинга), подставляет макросы (`{clickid}`, `{sub_id_1}` … `{sub_id_30}`, `{offer_id}` и др.) и делает редирект на оффер. Чтобы указать конкретный оффер из потока, добавьте его ID:

```html
<a href="/?_lp=1&offer_id=10">Оффер 10</a>
```

Если в потоке выбран только лендинг без оффера, лендинг открывается как финальная страница, а ссылка `/?_lp=1` ничего не делает (оффера нет).

## 🔗 Click API с токенами

### Что такое Click API?

Click API — это механизм для работы с интеграционными скриптами, когда вместо `campaign_id` используется уникальный токен кампании.

### Преимущества токенов
- **Совместимость с Keitaro** — существующие скрипты продолжат работать
- **Безопасность** — токен сложно угадать, ID легко перебрать
- **Гибкость** — можно менять кампании без изменения скриптов

### Как это работает

**Традиционный подход:**
```
https://tracker.com/click.php?campaign_id=123
```

**С токеном:**
```
https://tracker.com/click.php?token=abc123def456...
```

### Генерация токена

- **Длина**: 32 символа (hex)
- **Уникальность**: автоматическая генерация при создании кампании
- **Регенерация**: можно сгенерировать новый токен в редакторе

### Сохранение токенов при миграции

При импорте из Keitaro:
1. Токены из Keitaro автоматически переносятся в Orbitra
2. Сохраняется полная совместимость с существующими интеграциями
3. Интеграционные скрипты продолжат работать без изменений

### Где используется токен

- **Интеграционные скрипты** на лендингах
- **API запросы** от сторонних систем
- **Постбеки** от партнерских сетей
- **Вебхуки** от внешних сервисов

## 🔄 Миграция из Keitaro

### Подготовка дампа Keitaro

На сервере Keitaro выполните:

```bash
# 1. Подключитесь к Keitaro серверу
ssh root@YOUR_KEITARO_SERVER_IP

# 2. Создайте дамп настроек (без логов кликов)
bash -lc '
source /etc/keitaro/env/inventory.env

# Конфиг для подключения к БД
cat > /root/keitaro-mariadb.cnf <<EOF
[client]
user=$MARIADB_KEITARO_USER
password=$MARIADB_KEITARO_PASSWORD
host=127.0.0.1
port=3306
protocol=tcp
EOF
chmod 600 /root/keitaro-mariadb.cnf

# Создание дампа таблиц
TABLES="keitaro_affiliate_networks keitaro_groups keitaro_offers keitaro_domains keitaro_campaigns keitaro_campaign_postbacks keitaro_landings keitaro_streams keitaro_stream_filters keitaro_stream_offer_associations keitaro_stream_landing_associations keitaro_traffic_sources keitaro_ref_sources"

mysqldump --defaults-extra-file=/root/keitaro-mariadb.cnf \
  --single-transaction --quick --skip-lock-tables \
  "$MARIADB_KEITARO_DATABASE" $TABLES \
  | gzip > /root/keitaro_orbitra_full.sql.gz

ls -lah /root/keitaro_orbitra_full.sql.gz
'

# 3. Скачайте файл к себе
scp root@YOUR_KEITARO_SERVER_IP:/root/keitaro_orbitra_full.sql.gz .
```

### Импорт в Orbitra

1. Откройте **Миграции** в меню админки
2. Следуйте инструкции в блоке "Как создать бекап Keitaro"

## ♻️ Очередь S2S-постбеков с retry (с версии 0.9.6.0)

До 0.9.6.0 исходящие S2S-постбеки отправлялись синхронно прямо во время обработки входящего постбека (`fire-and-forget`): если эндпоинт партнёрки был недоступен, постбек терялся безвозвратно. Теперь постбеки доставляются надёжно.

**Как работает:**
1. При входящем постбеке (`postback.php`) каждая исходящая доставка добавляется в таблицу `s2s_postbacks_log` со `status='pending'` и макро-подставленным URL.
2. Воркер `postback_queue_cron.php` (запускается по cron каждую минуту) выбирает «должные» строки, выполняет HTTP-запрос и пишет результат.
3. Критерий успеха — HTTP `2xx-399`. Иначе — повтор с экспоненциальным backoff: **60с → 5м → 30м → 2ч → 24ч**. Всего 6 попыток (1 первая + 5 повторов), после чего строка помечается `status='failed'` (видна в логах S2S).
4. SSRF-проверка выполняется дважды: при постановке в очередь и перед отправкой. Хост, который резолвится в приватный/зарезервированный адрес, помечается `failed` без повторов; неудачный DNS считается временной ошибкой и уходит в повтор.
5. Строку, взятую в работу (`status='in_flight'`) и брошенную упавшим воркером, следующий запуск возвращает в очередь через 10 минут — иначе она была бы невидима для выборки, которая смотрит только на `pending`.

> ⚠️ **Без установленного крона очередь не разбирается и постбеки не уходят.** Это первое, что нужно сделать после обновления на 0.9.6.0.

**Установка воркера:** **Настройки → Автоматизация → Очередь постбеков**, кнопка «Установить cron доставки» — действие `postback_queue_install_user_cron` (ставит строку `* * * * *` в crontab пользователя). Удаление — `postback_queue_remove_user_cron`. Состояние воркера (last ping, processed/delivered/requeued/failed за последний запуск, счётчики по статусам) отдаёт `postback_queue_info` и показывает та же панель.

**Расширенные макросы** (раньше было 6, теперь поддерживаются все): `{subid}`, `{status}`, `{payout}`, `{currency}`, `{external_id}`, `{tid}`, `{campaign_id}`, `{cost}`, `{revenue}`, `{profit}`, `{sub_id_1}` … `{sub_id_30}`.

**Исправленный баг POST:** постбеки с методом POST теперь отправляют тело (раньше уходил пустой POST). Поля из query-string переносятся в `CURLOPT_POSTFIELDS` с `Content-Type: application/x-www-form-urlencoded`.

## 💰 Автоимпорт расходов из Facebook Ads / Google Ads (с версии 0.9.6.0)

Два новых engine агрегатора забирают дневной рекламный расход и атрибутируют его к кликам, так что отчёты ROI/прибыли больше не показывают нулевой расход.

**Engines** (в `aggregator_engines/`):
- **FacebookAdsEngine** — Facebook Marketing API `/act_<id>/insights`. Авторизация: long-lived User Access Token или System User Token + Ad Account ID.
- **GoogleAdsEngine** — Google Ads API (REST, v19, GAQL). Авторизация server-to-server OAuth2: `developer_token` + `client_id` + `client_secret` + `refresh_token` + `customer_id`. `refresh_token` не протекает; короткоживущий `access_token` получается автоматически и кешируется в таблице `oauth_tokens`.

**Атрибуция к кликам:** импортированный расход (таблица `cost_records`) распределяется по кликам через `UPDATE clicks SET cost = cost + ?`, группируя по дню и рекламному ID. Ключи join — `json_extract(clicks.parameters_json, '$.ad_id')` → `$.campaign_id` → `$.campaignid` (для ValueTrack), те самые ID, которые уже проставляются встроенными traffic-source-шаблонами Facebook и Google Ads.

**Настройка:** Администрирование → Агрегатор → новый connection с engine `facebook` или `google_ads`, поля форм генерируются динамически через `getRequiredFields()`. Тест подключения — кнопкой «Test Connection». Синхронизация — по cron (`aggregator_cron.php`) или вручную (кнопка Sync).
