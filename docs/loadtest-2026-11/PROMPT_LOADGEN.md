# Задача: провести нагрузочный тест Orbitra по методике CPA.RIP

Ты работаешь на VPS-генераторе (Ubuntu 24.04, 2 vCPU) в том же дата-центре, что и сервер с трекером Orbitra. Цель: повторить методику статьи CPA.RIP «Нагрузочное тестирование 4 бесплатных self-hosted CPA-трекеров» (16.11.2026) на Orbitra и получить цифры, сравнимые с их таблицами. Итог потом подведёт другой ассистент, поэтому **сырые данные важнее выводов**: ничего не округляй и не выбрасывай.

От Руслана ты получишь блок с параметрами трекера: `TRACKER_IP`, `CAMPAIGN_ALIAS`, `CAMPAIGN_ID`, `SSH_USER`, `DB_READ_CMD`, `RESET_CMD`, `XFF_TRUSTED`, `UNIQUENESS`. Пока его нет, готовь всё остальное.

## Правила

- На сервер трекера ты ходишь **только** как `ltcheck` и только для чтения базы, `/proc`, логов и запуска `RESET_CMD`. Ничего там не меняешь.
- Не подгоняй методику под результат. Если что-то в ней невозможно сделать как написано, сделай максимально близко и **запиши отклонение**.
- Пиши журнал всех действий в `/root/lt/LOG.md`.

## Подготовка

1. Поставь k6 (официальный apt-репозиторий Grafana или бинарник с GitHub), `sqlite3`, `python3`, `jq`. Запиши версии.
2. `ulimit -n 65535` для запусков k6. При необходимости подними `net.ipv4.ip_local_port_range` и включи `net.ipv4.tcp_tw_reuse=1` **на генераторе** (трекер не трогать). Запиши.
3. Сгенерируй SSH-ключ `ed25519` и выведи публичный ключ, чтобы Руслан передал его агенту трекера. После получения параметров проверь: `ssh ltcheck@TRACKER_IP` выполняет `DB_READ_CMD "select 1"`, читает `cat /proc/stat` и запускает `RESET_CMD`.
4. Смоук: `curl` на `http://TRACKER_IP/CAMPAIGN_ALIAS?sub1=smoke-x` → 302 на `https://offer.example/?cid=<uuid>`, и в базе есть строка с `sub1 = smoke-x` и тем же id.

## Методика (как в статье)

- **Ступени:** 20 → 40 → 80 → 160 → 320 → 480 запросов/с.
- Старт на 20 rps. Переход на следующую ступень: линейный разгон за 30 с, затем удержание 3 минуты. Измеряется только окно удержания (3 мин), разгон в статистику не входит.
- Таймаут ответа 5 с, редиректы **не следовать** (`redirects: 0`).
- Нагрузка в постоянном темпе (`ramping-arrival-rate`/`constant-arrival-rate`, `preAllocatedVUs` с запасом, `maxVUs` ~3000). Если k6 не успевает держать темп (`dropped_iterations > 0`), это ошибка генератора: зафиксируй её отдельно, не списывай на трекер.
- **У каждого запроса свой `event_id`** (уникальная строка: префикс прогона + ступень + VU + итерация). Он идёт в `sub1`, а в `sub2` — имя прогона.
- **Правильный ответ:** статус 302, `Location` начинается с `https://offer.example/?cid=`, cid в формате UUID.
- **Ступень успешна**, если за 3 минуты удержания: 0 неправильных ответов (не 302, неверный Location, таймаут, сетевая ошибка) **и** каждый `event_id` найден в `clicks` **ровно один раз**.
- **Ступень провалена** при любой ошибке ответа или записи, либо если трекер явно лёг. Тогда лестница прекращается, и выполняется **проверка восстановления**: 20 rps в течение 2 минут, по 10-секундным окнам фиксируется доля правильных редиректов и доля записанных кликов. Нужно найти момент, с которого всё снова 100%.

### Профили посетителей

Каждый запрос шлёт `X-Forwarded-For` (если `XFF_TRUSTED=no`, запиши это: тогда для трекера все посетители будут с одного IP, и профили неразличимы; не продолжай без подтверждения Руслана) и `User-Agent`.

- **Уники (`unique`):** каждый запрос — новый случайный публичный IP (только публичные диапазоны, никаких 10/8, 100.64/10, 127/8, 169.254/16, 172.16/12, 192.168/16) и UA из реального пула (десятки мобильных и десктопных UA) с уникальным суффиксом сборки. Ни одна пара IP+UA не повторяется.
- **Неуники (`repeat`), основной вариант:** пул из **10 000** постоянных посетителей (пара IP+UA). Каждый запрос — случайный посетитель из пула. При 480 rps один посетитель повторяется в среднем раз в ~20 с. Это повторные клики в пределах окна уникальности трекера.
- **Неуники, строгий вариант (`repeat-tight`), дополнительно:** пул из **50** посетителей, повторы чаще раза в секунду. Важно: у Orbitra есть защита от двойных кликов. Повтор той же пары IP+UA в пределах 2 секунд **не создаёт новую строку**, а получает cid предыдущего клика. В этом варианте считай **две** метрики: (а) строго по методике (найден ли `event_id`); (б) существует ли в базе cid из редиректа. Расхождение (а) и (б) — это ожидаемый эффект защиты, а не потеря. Опиши его цифрами отдельно, в основной результат не смешивай.

## Порядок прогонов

Перед каждым прогоном с нуля: `RESET_CMD`, пауза 60 с, проверка `/proc/loadavg` на трекере (< 0,5), смоук-запрос.

1. **unique, основной:** лестница 20 → 480, пока ступени проходят.
2. **repeat, основной:** то же самое.
3. Для каждого профиля возьми **максимальную пройденную ступень** и выполни её ещё **2 раза** на чистой базе: старт 20 rps → разгон 30 с → удержание 3 мин на этой ступени. Итого три результата на профиль, как в статье.
4. **repeat-tight:** одна лестница до первого провала по метрике (б), обе метрики записать.
5. Если ни на одном профиле не было провала до 480, дополнительно (по желанию, после основного) попробуй 640 и 800 на униках, чтобы найти начало перегрузки. Отметь это как вне методики статьи.

## Что измерять на каждой ступени (окно удержания)

- запросов отправлено, правильных 302, неправильных по типам (таймаут, не-302, неверный Location, сетевая ошибка), `dropped_iterations`;
- latency: среднее, p50, p95, **p99 по всем запросам, включая ошибки и таймауты** (так считает статья), max;
- **CPU трекера**: среднее за окно удержания по разнице `/proc/stat` в начале и в конце окна, плюс пиковые значения по 5-секундным снимкам. Также средний `loadavg`;
- CPU генератора (чтобы доказать, что он не был узким местом);
- **сверка с базой** после ступени (подожди 5 с): выгрузи все `sub1` кликов этого прогона (`WHERE campaign_id = CAMPAIGN_ID AND json_extract(parameters_json,'$.sub1') LIKE '<префикс ступени>%'`) и сравни с журналом `event_id` ответов: не найдено, найдено больше одного раза. Для cid из редиректов проверь, что такая строка в `clicks` есть;
- строки в `var/spool/clicks.log` трекера (если файл есть) — клики, отложенные на запись;
- ошибки из логов php-fpm, nginx (`error.log`: `worker_connections`, `upstream`, `Resource temporarily unavailable`) и `var/logs/` Orbitra за окно ступени.

Журнал ответов пиши построчно (JSON lines: `event_id`, статус, Location/cid, длительность, ошибка). Файлы большие, сжимай их gzip после ступени.

## Результат

В `/root/lt/results/`:
- `summary.md`: таблицы в формате статьи. (1) Максимальная пройденная ступень для «уники» / «неуники» и где началась перегрузка. (2) p99 / CPU на **160 rps уники** и **80 rps неуники**. (3) Полная таблица всех ступеней всех прогонов. (4) repeat-tight с метриками (а) и (б). (5) Восстановление после перегрузки. (6) Все отклонения от методики;
- `summary.json` с теми же числами;
- `env.md`: железо обоих серверов (`lscpu`, `free -m`, версия ядра), версии k6 и Orbitra, параметры из блока Руслана, пинг между серверами (`ping -c 20`);
- сырые журналы и k6 summary по каждой ступени;
- архив `/root/lt/results.tar.gz` со всем перечисленным.

В конце выведи Руслану `summary.md` целиком и путь к архиву. **Без собственных выводов о том, лучше ли Orbitra других трекеров**: только числа и наблюдения.
