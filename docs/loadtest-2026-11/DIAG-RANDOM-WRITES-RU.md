## 8. Арифметический аудит — полная раскладка по b-tree (исправляет базовую линию §6)

Базовая линия §6 (2,11) была намерена на базе с СЧЕТЧИК-паттерном IP (только
замерные клики со случайными IP): в такой базе ip-индексы держат узкую полосу
ключей и грязь случайных вставок концентрируется — базовая занижена на
~1,6 стр/клик. Оба варианта перемерены на одинаково-случайных базах, с
атрибуцией ПО БАТЧУ (чекпоинт переносит каждый батч отдельно; объединение с
делением на 2× занижало повторяющиеся страницы, например хвосты групп
ad_ref). Полные таблицы (leaf/internal по каждому b-tree, freelist = 0;
17 936 страниц freelist у варианта b — это сам дропнутый ip_created) — в
английском оригинале §8. Краткая суть:

| | базовая | вариант b | разница |
|---|---|---|---|
| всего стр/клик | **3,75–3,77** | **1,82–1,83** | −1,93 |
| PK (uuid4→uuid7) | 0,99 | 0,01 | −0,98 |
| idx_clicks_ip_created | 0,97 | — | −0,97 |
| ip_ua / ad_ref / heap / прочие | 1,02 / 0,55 / 0,20 / 0,04 | 1,03 / 0,55 / 0,20 / 0,04 | — |

Аудит сходится: разница ровно равна двум убранным вкладчикам. Другие таблицы
(по коду): per-click пишет только clicks; meta_matching_keys — раз на
установку, click_browser_checks — только при прогоне проверки, system_logs —
только на ошибках — атрибуция подтверждает (вне clicks-семьи ничего нет).
Для диска: исправленная базовая = 3,75 × 4КБ × 480 ≈ **1 760 случайных IOPS**
(стендный потолок 700 — шансов не было); шаг 1 один даёт 860 IOPS — всё ещё
выше бюджета; следующие случайные вкладчики — ip_ua (0,99) и ad_ref (0,54),
под них и задуманы шаг-2 (ipua_hash, 0,47) и возможный ad_ref-фоллоуап.

## 9. Реализм ad_ref + окно коалесценции 960 кликов (вход для решения по шагу 2)

**ad_ref в профиле CPA.RIP = NULL**: кит запрашивает только
`?sub1=<eid>&sub2=<run>`, а orbitraBuildClickRow не ставит ad_ref без
реального ad_id/creative_id. Значение 0,54 из §8 — артефакт лабы (5000
циклящихся значений, которых стенд не шлёт). В окне 960: NULL-профиль —
**0,008/клик** (NULL-хвост, аппенд); 40 реальных значений — 0,126; частичный
индекс (WHERE ad_ref IS NOT NULL) — EXPLAIN: планировщик использует его даже
без явного `IS NOT NULL` в запросе (IN-список достаточен); по записи ничего
не меняет (NULL-клики перестают трогать индекс, Δ итога 1,594 vs 1,611) —
**это оптимизация размера, не записи**.

**Окно 960** (одно PASSIVE-окно при 480 rps, 20 окон, атрибуция по окну):
вариант b (NULL) = **1,611** (ip_ua 1,221+0,106i, heap 0,20, PK 0,016);
b+ipua_hash = **1,295** (хэш 0,938+0,073i). Полные таблицы — §9 EN. Для
диска: b ≈ 770 случ. IOPS@480 (чуть выше потолка ~700); b+hash ≈ 620 —
влезает с ~10% запасом. Решение по шагу 2 одной строкой: **b один, скорее
всего, всё ещё насытит перенос; b+hash — в бюджете** (лаба; стенд решает).
