# Задача: найти, на что тратится время клика на этом сервере

Тест закончен, результаты у Руслана. Главная странность: даже на 20 rps каждый уникальный клик отвечает не быстрее ~26 мс (p50 44 мс), хотя CPU сервера ~6%. Повторный клик, который не пишет в базу (защита от двойных кликов), отвечает за ~5 мс. На 160 rps задержка за 3 минуты растёт с 30 до 600 мс, CPU при этом ~25%, а loadavg растёт до 9. То есть процессы чего-то **ждут**, а не считают.

Тот же код Orbitra 1.9.4 в другом окружении (2 vCPU, k6 на той же машине, только Sypex Geo, быстрый локальный диск) даёт на 160 rps p50 5 мс / p99 11 мс, а на 480 rps — 0 ошибок. Значит, разница либо в **диске** этого VPS (скорость fsync), либо в **гео-базах** (Orbitra Geo 519 МБ, Mobile Operator, BotDB), либо в чём-то ещё в окружении.

## Правила

- Код Orbitra не меняешь. Временные изменения разрешены только из списка ниже, каждое откатываешь сразу после замера и пишешь в отчёт: что сделал, как откатил.
- Перед замерами сбрось базу: `/usr/local/bin/orbitra-lt-reset`.
- Отчёт в `/root/loadtest/DIAG.md`: команды, сырые цифры, вывод.

## Замеры

1. **Диск.** Где лежит база (`df -h /var/www/orbitra`, `lsblk`, `mount | grep ' / '`) и тип диска (локальный NVMe или сетевой). Затем задержка синхронной записи:
   ```
   cd /var/www/orbitra/var && dd if=/dev/zero of=fsync.test bs=4k count=500 oflag=dsync; rm -f fsync.test
   ```
   Если есть `fio` (или его можно поставить), дополнительно:
   ```
   fio --name=fs --filename=/var/www/orbitra/var/fio.test --size=64m --rw=write --bs=4k --ioengine=sync --fdatasync=1 --runtime=20 --time_based; rm -f /var/www/orbitra/var/fio.test
   ```
   Нужны среднее время одного fdatasync и p99.

2. **Режим SQLite, который видит приложение:** `journal_mode`, `synchronous`, `wal_autocheckpoint`, `busy_timeout`. Выясни через PHP с подключением `config.php` (одноразовый скрипт в `/tmp`, запуск от www-data), а не через sqlite3 CLI: CLI покажет свои значения, а не приложения.

3. **Время одного клика без нагрузки.** 200 последовательных запросов с локальной машины, каждый — новый посетитель:
   ```
   for i in $(seq 1 200); do curl -s -o /dev/null -w "%{time_total}\n" -A "Mozilla/5.0 diag$i" -H "X-Forwarded-For: 85.$((i%200+1)).10.$((i%250+1))" "http://127.0.0.1/loadtest?sub1=diag-$i"; done | sort -n | awk '{a[NR]=$1} END {print "p50",a[int(NR*0.5)],"p90",a[int(NR*0.9)],"p99",a[int(NR*0.99)]}'
   ```
   Затем то же самое, но 200 раз **один и тот же** посетитель (повтор → без записи в базу). Сравни.

4. **Системные вызовы одного клика.** Пока в цикле из п. 3 идут клики, сними на 15 с:
   ```
   strace -f -c -p $(pgrep -d, -f "php-fpm: pool") -o /tmp/strace_summary.txt
   ```
   (или `strace -f -T -e trace=fsync,fdatasync,pwrite64,pread64,openat,flock,fcntl,connect,sendto,recvfrom`). Нужно: какие вызовы занимают время, сколько fsync/fdatasync на один клик и сколько они длятся, нет ли сетевых соединений (`connect`) наружу на пути клика.

5. **Гео-базы.** Повтори п. 3 (новые посетители), временно **переименовав** гео-файлы Orbitra Geo, Mobile Operator и BotDB (не Sypex) в `*.off`. Сравни p50/p99 с п. 3. **Сразу верни имена** и проверь, что панель снова видит базы.

6. **WAL под нагрузкой.** Если сможешь дать небольшую нагрузку сам (`ab -n 20000 -c 32` или цикл curl в фоне, только новые посетители), следи раз в 5 с за размером `orbitra_db.sqlite-wal` и временем ответа. Растёт ли WAL без конца? Совпадает ли рост задержки с ростом WAL? Есть ли в логах `database is locked`?

7. **Пул php-fpm и nginx:** `pm`, `pm.max_children`, `listen.backlog` из `/etc/php/*/fpm/pool.d/www.conf`, `worker_connections`/`worker_processes` из `nginx.conf`. Только прочитать.

## Что вернуть

Короткая таблица: dsync-запись (мс на операцию), p50/p99 одного клика (новый посетитель / повтор / без гео-баз), число и длительность fsync на клик, рост WAL. Плюс одна фраза: на что, по цифрам, уходит время клика. После этого ничего не меняй и жди.
